# Aurora Workspace — ฉบับ 3: งานร้านต้องไปต่อได้

วันที่ 18 ตุลาคม 2569 · ชุดข้อมูลตัวอย่าง ณ 17 ตุลาคม 2569 · สถานะ: แผนและต้นแบบข้อมูลตัวอย่าง ก่อนพัฒนาแอปจริง

ฉบับนี้แก้ช่องว่างของแนวหน้าจอก่อนหน้า โดยให้กราฟ การส่งสินค้า และการแบ่งเงินเป็นส่วนหลักของการออกแบบ ไม่ซ่อนไว้หลังเมนูที่ไม่มีขั้นตอนทำงานต่อ ข้อกำหนดในเอกสารนี้มีลำดับสูงกว่าข้อเสนอฉบับเก่าที่ขัดกัน ส่วนสัญญาประวัติถาวรยังอ้างอิง HISTORY-EDITING.md

## หน้าตาและการใช้งาน

- Aurora ใช้แสง violet–mint บนพื้นที่หัวเรื่องและสีเน้น ส่วนข้อมูลเป็นพื้นทึบเพื่ออ่านจำนวนและรายการได้ง่าย รองรับ appearance สว่างและมืด
- เมนูหลักแสดง “รอส่งสินค้า” และ “แบ่งเงิน” โดยตรง ทั้ง desktop และทางลัดมือถือ
- ตารางแบ่งหน้าครั้งละ 8 รายการ เพื่อลดหน้าจอที่ยาวเกินไป ข้อมูล CSV แสดงให้เลือกคัดลอกตามช่วงเวลา
- ลำดับหน้าภาพรวม: งานวันนี้ → ตัวเลขหลัก → กราฟยอดขาย/เงินรับ/กำไร → ออเดอร์ล่าสุดและสินค้าขายดี
- แบบขายใหม่ใช้ฟอร์มกับสรุปข้างกันบน desktop และเรียงต่อกันบนมือถือ เห็นการแบ่งเงินก่อนยืนยัน ข้อนี้แทนแนว wizard 3 ขั้นของฉบับแรก
- ทุกหน้าที่เปลี่ยนข้อมูลมีประวัติร่วมกัน การแก้ไขใช้เหตุผลและหน้าตรวจค่าก่อน–หลัง ไม่ล็อกเพราะวันที่เก่า

## กราฟและตัวเลขที่ต้องมีในแอปจริง

| กราฟ | ฐานข้อมูลและความหมาย | ทางไปต่อ |
|---|---|---|
| ยอดขาย / รับจริง / กำไรหลังแบ่งส่วนตัว | วันขายกับวันรับเงินจริงแยกกัน; กำไรหักทุน ค่าส่ง ค่าธรรมเนียม และส่วนตัว ยังไม่รวมค่าแอดและส่วนกลาง | เลือกช่วงเวลาและวันที่ เปิดรายการต้นทาง |
| เงินรับ–เงินจ่าย | บัญชีเงินสดตามวันที่ รวมเงินทุนซื้อ ถอนส่วนตัว เติมเครดิต และคืนเงิน | เปิดหรือแก้รายการที่เชื่อมกัน |
| สินค้าขายดี | จำนวนจากออเดอร์ที่ไม่ยกเลิกในช่วงที่เลือก | เปิดสินค้า / ออเดอร์ |
| สัดส่วนแผนแบ่งเงิน | ใช้ส่วนตัว / แอด / ทุน / ค่าใช้จ่ายขาย / เหลือ | ปรับอัตรารายออเดอร์ เห็นผลกระทบก่อนบันทึก |
| ประสิทธิภาพโฆษณาในขั้นพัฒนา | ค่าแอดจริง เทียบยอดขายและกำไรที่ผูกแคมเปญ แยกยอดประมาณการจากแพลตฟอร์ม | ลงยอดใช้จริงและกระทบเครดิตอย่างถูกต้อง |

ไม่มีตัวเลขเติบโตหรือเป้าหมายที่แต่งขึ้นเพื่อให้หน้าดูเต็ม หากช่วงก่อนหน้าไม่มีข้อมูล แสดงว่าไม่มีฐานเปรียบเทียบ

## เส้นทางขาย → ส่ง → แบ่งเงิน

1. เลือกสินค้าและจำนวน ใส่ราคาขาย ค่าส่ง ค่าธรรมเนียม ลูกค้า วันที่ และการชำระเต็ม/ผ่อน
2. กำหนดใช้ส่วนตัวเป็น % ของยอดขายเต็ม และเก็บยิงแอดเป็นบาทต่อชิ้น ผูกแคมเปญ
3. ตรวจสรุปยอดขาย เงินรับครั้งนี้ ค้างชำระ กำไร และเงินแบ่งก่อนยืนยัน
4. บันทึกขายลดสต็อกครั้งเดียว สร้างเงินรับตามที่รับจริง และเข้าสู่คิวรอส่ง
5. เลือกจำนวนส่งบางส่วนได้ รวมหลายออเดอร์เมื่อเป็นผู้รับเดียวกัน กรอกขนส่ง เลขพัสดุ และเฉพาะค่าส่งที่ยังไม่บันทึก
6. ตรวจแล้วส่ง จำนวนรอส่งลดลง สต็อกและเงินรับไม่เปลี่ยน ค่าส่งเพิ่มเป็นเงินจ่ายหนึ่งรายการ
7. แสดงเงินแบ่งเฉพาะจำนวนที่ส่ง โดยปัดเศษสะสมเพื่อให้ส่งหลายครั้งแล้วได้เท่ากับส่งครบครั้งเดียว
8. เปิดพัสดุเดิมแก้เลข/ค่าส่งได้ ปรับเงินจ่ายเดิมตามผลต่าง ยกเลิกบันทึกส่งคืนจำนวนเข้ารอส่ง แต่ไม่คืนเงินหรือสต็อก

ตัวอย่าง: ขาย 2 × 390 = 780 บาท รับมัดจำ 300 ใช้ส่วนตัว 10% และแอด 35 บาท/ชิ้น → แผนส่วนตัว 78 แอด 70 ค้างรับ 480; ส่ง 1 ชิ้นแสดงส่วนตัว 39 และแอด 35 ไม่ถือว่าได้โอนเงินแล้ว

## การแบ่งเงินที่ไม่ทำให้เงินสดสับสน

- ใช้ส่วนตัว = ยอดขายเต็ม × เปอร์เซ็นต์ ไม่ใช่เปอร์เซ็นต์ของกำไร
- แอดแบบต่อชิ้น = จำนวน × อัตราที่บันทึกไว้กับออเดอร์ ไม่เปลี่ยนอัตโนมัติตามค่าเริ่มต้นใหม่
- แผนคงเหลือ = ขาย − ทุน − ค่าส่ง − ค่าธรรมเนียม − ส่วนตัว − เงินเก็บยิงแอด หากติดลบแสดงเตือน
- แผนไม่สร้างรายการถอนเงินหรือเติมเครดิตจริง ผู้ใช้บันทึกการจ่ายจริงแยกต่างหาก
- รายการผ่อนแสดงเงินค้าง ไม่เรียกแผนแบ่งว่าเงินพร้อมถอน
- เครดิตโฆษณา: เติมเครดิตเป็นเงินจ่ายจริง ยอดใช้แอดเป็นการใช้เครดิต ต้องไม่ลงเงินจ่ายซ้ำทั้งสองขั้น
- กำไรไม่เท่ากับเงินเข้าออกสุทธิ และเงินเข้าออกในช่วงไม่ใช่ยอดคงเหลือบัญชีหากไม่มีเงินยกมา

ต้นแบบใช้วิธีแอดต่อชิ้น ส่วนวิธีเดิมที่แบ่งตาม % ของกำไรแคมเปญต้องคงไว้ในขั้นพัฒนา ไม่เปลี่ยนข้อมูลเก่าเป็นต่อชิ้นโดยพลการ

## ความครอบคลุมและสิ่งที่ต้องพัฒนาต่อ

| พื้นที่เดิม | จุดเข้าถึงใหม่ | ที่ทดลองได้ในฉบับนี้ | งานที่ยังต้องทำในแอปจริง |
|---|---|---|---|
| Home / tasks | ภาพรวม | กราฟ ช่วงเวลา คิวงานและทางไปต่อ | เทียบช่วงก่อน เป้าหมายที่ผู้ใช้ตั้ง การแจ้งเตือนและงานครบทุกชนิด |
| Sell | บันทึกขาย | ขายเต็ม/ผ่อน ค่าใช้จ่าย แบ่งเงิน ตรวจผลก่อนบันทึก | validation ฝั่ง server ความขัดแย้งหลายเครื่อง รายละเอียดการคืนสินค้าหลังส่ง |
| Shipments | รอส่งสินค้า | ส่งบางส่วน เลขพัสดุ ค่าส่ง แบ่งเงิน แก้/ยกเลิกพัสดุ | ชื่อ/ที่อยู่ผู้รับที่เป็นโครงสร้าง การติดตามขนส่ง การส่งออกครบแบบเดิม |
| Profit | แบ่งเงิน | สัดส่วนรายออเดอร์ รวมช่วงเวลา ถอนส่วนตัว/เติมเครดิตแบบจำลอง | เก็บแผนย้อนหลังถาวร แอดแบบ % เดิม และกระทบยอดเงินยกมา |
| Stock | สินค้าและสต็อก | ค้นหา เพิ่ม แก้ชื่อ/ราคา/ทุน ตรวจนับ | SKU matrix หลายสีไซซ์ นำเข้า ส่งออก ย้ายสินค้า และประวัติล็อตครบ |
| Pending / receiving | รับสินค้า | สั่งซื้อ รับบางส่วน จ่ายทุน และเพิ่มสต็อก | กระจายค่าขนส่งล็อต ตรวจยอดชำระเดิม และแก้การรับสินค้าที่ถูกขายไปแล้ว |
| Preorder | พรีออเดอร์ | สร้าง รับมัดจำ ของพร้อม เปลี่ยนเป็นขายโดยไม่รับเงินซ้ำ | การจัดหาผูกล็อต ยกเลิก/คืนเงิน/แก้หลังส่งต่อผ่านรายการเชื่อมโยง |
| Installment | ออเดอร์ / ผ่อน | กรองค้างชำระ รับเพิ่ม แก้ราคาโดยคงเงินรับ | วันครบกำหนด ค้างชำระหลายงวด และการติดตามลูกค้า |
| Transactions | เงินและรายงาน | รับ/จ่าย แก้รายการหรือเปิดต้นทาง CSV ตามช่วงเวลา | ledger correction ถาวร ภาษี/บัญชีตามการใช้งานจริง และกระทบยอด |
| Ads | การตลาด | แคมเปญ งบ ยอดใช้ เครดิต และเงินเก็บยิงต่อ | วิธีประมาณการงบเดิม แยกรายวัน และการเชื่อมแพลตฟอร์มหากผู้ใช้ต้องการ |
| Report | ภาพรวม + เงินและรายงาน | แนวโน้มและยอดขายดี ข้อมูลเงินสด | รายงานครบทุกช่วง/มิติแบบเดิม รวมสินค้าคืน/ยกเลิกและ CSV แต่ละรายงาน |
| History | ประวัติทั้งหมด | กรองหมวด ค่าเดิม/ใหม่ เหตุผล เปิดแก้ใหม่ และนำช่องที่แก้ได้กลับมาใช้ | auth, actor จริง, เวลา server, revisions, atomic audit, idempotency, multi-device conflict |
| Tools / backup / AI | ตั้งค่าและเครื่องมือ | ตั้งค่าเริ่มต้นร้าน | สำรอง/กู้คืนจริง ตรวจไฟล์นำเข้า AI อ้างอิงข้อมูล และบันทึกประวัติการใช้เครื่องมือ |

“ทุกฟีเจอร์มีประวัติและแก้ไขได้” เป็นข้อกำหนดของระบบที่จะพัฒนา ไม่หมายความว่าทุก dependency ในตารางถูกทำเสร็จในต้นแบบแล้ว รายการที่ถูกส่ง/ขายต่อ/คืนเงินจริงต้องแก้ผ่าน correction ที่สอดคล้องกัน ไม่ลบหลักฐานธุรกรรมเก่า

## ลำดับลงมือพัฒนา

1. ตรึงฐานสูตรเงินและ regression จากโมดูลเดิม ก่อนย้ายหน้าจอ
2. ทำ Aurora shell, component, navigation, responsive และภาษาสถานะร่วมกัน
3. ย้ายขาย–ผ่อน–ส่ง–แบ่งเงินเป็นเส้นทางแรก เก็บ audit ทุก mutation พร้อมตรวจผลกระทบและ idempotency
4. ย้ายสต็อก–รับเข้า–พรีออเดอร์ โดยตรวจความสัมพันธ์ของล็อตและจำนวนที่ขายไปแล้ว
5. ย้ายการเงิน–แอด–รายงาน พร้อมกราฟที่ตรวจย้อนกลับถึงรายการต้นทางได้
6. เครื่องมือสำรอง/กู้คืน/AI, accessibility, regression และแผนย้ายข้อมูล โดยรักษาฟีเจอร์เดิมตามตาราง

เกณฑ์พร้อมใช้: ไม่มีปุ่มหลักที่ไปหน้าว่าง ตัวเลขทุกจุดอธิบายฐานคำนวณได้ ประวัติอยู่ถาวร แก้ย้อนหลังผ่านเส้นทางที่ถูกต้อง และทุก mutation มีกรณีตรวจซ้ำ/ย้อนกลับ/ความขัดแย้งจากอีกเครื่อง
