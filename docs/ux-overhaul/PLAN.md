# Crazsix — แผนปรับ UX/UI และฟีเจอร์ทั้งระบบ

วันที่: 18 ตุลาคม 2569 · ฉบับปรับปรุง 3: Aurora Workspace + กราฟ/รอส่ง/แบ่งเงิน · สถานะ: แผนและแนวหน้าจอก่อนพัฒนา

แนวหน้าจอล่าสุดและลำดับพัฒนา: [Aurora Workspace ฉบับ 3](AURORA-WORKSPACE.md) · [หน้าภาพรวม](workspace-desktop.png) · [หน้ารอส่ง](workspace-shipping.png) · [แบ่งเงิน](workspace-allocation.png)

ข้อเสนอฉบับ 3 แทนรายละเอียดการจัดหน้าและเมนูที่ขัดกันด้านล่าง โดยแยก “รอส่งสินค้า” และ “แบ่งเงิน” เป็นทางเข้าหลัก และเก็บกราฟเดิมไว้ในขอบเขตที่ต้องรักษา

## 1. ผลลัพธ์ที่ต้องการ

ทำให้เจ้าของร้านเปิดแอปแล้วรู้ว่าวันนี้ต้องทำอะไร ขายของและรับของได้เร็ว ตามเงินและพัสดุได้ต่อเนื่อง และเข้าใจที่มาของตัวเลข โดยรักษาประวัติสต็อก เงิน และต้นทุนเดิม ทุกฟีเจอร์ที่เปลี่ยนข้อมูลต้องมีประวัติและเปิดกลับมาแก้ไขได้โดยไม่มีช่วงเวลาปิดแก้จากอายุรายการ

รอบนี้ส่งมอบแผนและแนวหน้าจอเท่านั้น ยังไม่ได้เปลี่ยนแอปจริงหรือข้อมูลร้าน ตัวเลขและชื่อลูกค้าในแนวหน้าจอเป็นข้อมูลสมมติ ไม่ใช่ข้อมูลจาก Firestore

ข้อกำหนดเพิ่มในฉบับนี้: [ประวัติและแก้ไขทุกฟีเจอร์](HISTORY-EDITING.md) · ภาพล่าสุด: [Aurora desktop](aurora-desktop.png), [ประวัติทั้งหมด](aurora-history.png), [ตรวจผลก่อนแก้ไข](aurora-edit-review.png), [ประวัติบนมือถือ](aurora-history-mobile.png)

ผู้ใช้หลักที่ตั้งสมมติฐานไว้คือเจ้าของร้านเสื้อผ้าขนาดเล็ก ใช้คอมพิวเตอร์ดูภาพรวมและใช้มือถือขาย/รับเงิน/จัดส่ง ต้องยืนยันกับเจ้าของร้านก่อนตรึงรายละเอียด ไม่ถือว่าสมมติฐานนี้ผ่านการวิจัยผู้ใช้แล้ว

## 2. สิ่งที่ตรวจพบจากระบบปัจจุบัน

สำรวจ `index.html`, `css/styles.css`, โมดูลใน `js/`, ชุดทดสอบ และเปิดหน้าจอจริงผ่าน Playwright โดยแทน Firebase ด้วยฐานข้อมูลในหน่วยความจำจาก `tests/helpers.js` บล็อกการเชื่อมต่อภายนอก ไม่อ่านหรือเขียนข้อมูลร้านจริง

| หลักฐาน | ผลต่อการออกแบบ |
|---|---|
| เมนูหลัก 12 รายการใน `tabMeta` และ `render()` ของ `js/app.js` | จัดลำดับตามงานร้านและรวมหน้าที่เกี่ยวข้อง โดยเก็บทางลัดไปงานสำคัญ |
| หน้าขายมี 12 ช่องที่มองเห็นได้เมื่อใช้สินค้าเพียงหนึ่งกลุ่ม จาก `renderSellTab()` | แยกเลือกสินค้า → การรับเงิน → ตรวจสอบ และเปิดตัวเลือกเพิ่มเติมเมื่อจำเป็น |
| ปุ่มบันทึกการขายอยู่ก่อนช่องผ่อนชำระและข้อมูลลูกค้าใน DOM | ย้ายปุ่มยืนยันไปหลังสรุปข้อมูลครบ ลดโอกาสกดก่อนกรอกจบ |
| สต็อกมี 6 พื้นที่ย่อยใน `setupStockWorkspace()` | แยกรายการสินค้า งานรับเข้า และประวัติให้ค้นหาง่ายขึ้น |
| หน้าแรกมีการ์ดสรุป 5 ใบ กราฟ งานติดตาม และรายการสินค้า | ให้คิวงานวันนี้เด่น ลดเนื้อหาซ้ำกับหน้าสต็อก |
| ป้าย “เงินสุทธิ” ใช้สูตรรายรับ − รายจ่าย ขณะที่มีกำไรขายและเงินแบ่งส่วนตัวอีกชุด | ใช้ชื่อที่บอกสูตรและฐานเวลา แยกเงินสดสุทธิ กำไร และเงินแบ่งใช้ส่วนตัว |
| งานรับเข้าบางป้ายรวม `pendingOrders` กับ `incomingPreorders()` | แยก “ร้านสั่งเข้าสต็อก” กับ “จัดหาตามจองลูกค้า” ทั้งจำนวนและทางไปต่อ |
| `app.js` 4,884 บรรทัด และ CSS 2,779 บรรทัด ณ วันสำรวจ | แยก shell, state ของฟอร์ม, UI รายหน้า และส่วนคำนวณทีละส่วน |
| สต็อกมีค้นหา/กรอง/ส่งออก ตรวจนับ ประวัติแก้ยอด รองรับหลายขนาดจริงแล้ว | ปรับการเข้าถึงของที่มีอยู่ ไม่สร้างฟีเจอร์ซ้ำ |
| มี focus trap, skip link, dark/light, ป้องกันกดซ้ำและการเขียนทับจากอีกเครื่องแล้ว | รักษาความสามารถเดิมและทดสอบซ้ำระหว่างเปลี่ยน UI |
| ข้อมูล 7 ชนิดเก็บเป็นอาร์เรย์ต่อเอกสาร มี snapshot conflict check ใน `firebase-service.js` | UI รุ่นแรกใช้สัญญาข้อมูลเดิม การเปลี่ยนโครงสร้างฐานข้อมูลแยกเป็นงานภายหลัง |
| `firestore.rules` ปัจจุบันมี `allow read, write: if true` และไม่มีขั้นตอนเข้าสู่ระบบ | เพิ่มงานกำหนดผู้ใช้และสิทธิ์ก่อนขยายการใช้งานข้อมูลลูกค้า ไม่ถือว่าการทำหน้า login เพียงอย่างเดียวแก้สิทธิ์แล้ว |

ภาพฐานอ้างอิง: [หน้าแรก](current-home-desktop.png), [สต็อก](current-stock-desktop.png), [ขายบนคอมพิวเตอร์](current-sell-desktop.png), [ขายบนมือถือ](current-sell-mobile.png)

การเปิดตรวจ 10 หน้าไม่พบ JavaScript page error กับข้อมูลชุดนี้ หน้าขายที่กว้าง 390px ไม่มีการล้นแนวนอนทั้งเอกสาร นี่เป็นการสำรวจหน้าจอ ไม่ใช่ผลทดสอบธุรกิจครบทุกกรณีหรือหลักฐานว่าทุกหน้าไม่มีปัญหา

## 3. หลักการ UX ใหม่

1. **เริ่มจากงานวันนี้**: คิวรอส่ง/รอรับเงิน/เกินนัดขึ้นก่อนกราฟ กดถึงรายการนั้นพร้อมตัวกรองได้
2. **ทำทีละเรื่อง**: หนึ่งหน้ามีงานหลักหนึ่งอย่าง ฟอร์มแสดงเฉพาะสิ่งที่ต้องใช้ในขั้นนั้น
3. **ตรวจผลก่อนบันทึก**: แสดงสต็อกที่ลด เงินที่รับ หนี้ที่เหลือ และรายการบัญชีที่จะเกิด
4. **ทุกยอดตรวจที่มาได้**: แตะตัวเลขเพื่อดูรายการ สูตร ช่วงเวลา และรายการที่ไม่นับ
5. **สถานะอ่านแล้วรู้ว่าทำอะไรต่อ**: ใช้คำกริยาและปุ่มตรงงาน เช่น “รับชำระเพิ่ม”, “บันทึกส่งแล้ว”
6. **มือถือทำงานจริงได้**: ปุ่มสำคัญอยู่ใกล้นิ้ว ช่องตัวเลขเปิดแป้นที่เหมาะสม ข้อมูลสำคัญไม่อาศัย hover
7. **ผิดพลาดแล้วทำต่อได้**: เก็บข้อมูลฟอร์ม แจ้งจุดผิด และให้ลองใหม่โดยไม่สร้างธุรกรรมซ้ำ

8. **ประวัติและแก้ไขเป็นส่วนหลัก**: แต่ละรายการมีข้อมูลปัจจุบัน ประวัติ ค่าเดิม/ค่าใหม่ และทางแก้ย้อนหลัง รายการปิดงานหรือเก็บถาวรยังเปิดตรวจและสร้างรายการแก้ไขได้

## 4. โครงสร้างเมนูใหม่และการย้ายฟีเจอร์เดิม

### เมนูบนคอมพิวเตอร์

| เมนูใหม่ | หน้าย่อย/เนื้อหา | ของเดิมที่ย้ายมา |
|---|---|---|
| วันนี้ | คิวงานด่วน ภาพรวมช่วงที่เลือก กิจกรรมล่าสุด | home + tasks |
| สินค้า | รายการสินค้า รายละเอียดตัวเลือก ตรวจนับ ประวัติปรับยอด | stock: inventory + count |
| รับเข้า | สั่งเข้าสต็อก รับบางส่วน ประวัติล็อต ต้นทุน/ค่าส่งรับเข้า | stock: add + pending + history + shipping |
| คำสั่งซื้อ | ทั้งหมด รอส่ง ผ่อนชำระ จองลูกค้า ยกเลิก/คืนเงิน | sell + shipments + installment + preorder |
| การเงิน | เงินเข้าออก กำไร รายงาน | tx + profit + report |
| การตลาด | เครดิตกลาง แคมเปญ ค่าแอด ยอดจริง/ประมาณการ ผลลัพธ์ | ads |
| ประวัติทั้งหมด | ค้นหา/กรองกิจกรรม ข้อมูลก่อน–หลัง ผู้แก้ เหตุผล เปิดรายการและแก้ไข | รวมประวัติทุกฟีเจอร์และเพิ่มประวัติส่วนที่ยังไม่มี |
| ตั้งค่าและข้อมูล | รูปลักษณ์ สำรอง/นำเข้า ส่งออก จัดการสิทธิ์ | data-tools + theme; สิทธิ์เป็นงานเพิ่ม |

“บันทึกขาย” เป็นปุ่มหลักใน shell และเปิดทางเดินงานเดียวกันจากสินค้า/คำสั่งซื้อ ไม่มีฟอร์มขายหลายชุดที่คำนวณต่างกัน

“วิเคราะห์แนวโน้ม” ย้ายเป็นข้อมูลช่วยตัดสินใจในรายงาน/การตลาด พร้อมข้อความว่าเป็นกฎวิเคราะห์ในเครื่อง การเชื่อม AI ภายนอกเป็นงานแยกที่ต้องมีการประเมินความจำเป็นและข้อมูลที่ส่งก่อน

เมนูมือถือ: วันนี้ · สินค้า · ขาย · คำสั่งซื้อ · เพิ่มเติม โดย “เพิ่มเติม” เปิดรับเข้า การเงิน การตลาด ประวัติทั้งหมด ตั้งค่า ทุกเมนูยังเข้าถึงได้ คิวงานด่วนอยู่หน้าแรกไม่ต้องจำเมนู

### URL และการกลับไปทำงาน

- เก็บหน้าปัจจุบัน แท็บ ตัวกรอง และรหัสรายการใน URL รองรับ refresh, Back/Forward และเปิดรายการตรงจากคิวงาน
- เลือกแนวทาง hash route ที่ต่อยอดของเดิมได้ เช่น `#orders?view=shipping&id=...` พร้อมแปลง hash เดิม เช่น `#shipments`, `#installment`, `#preorder`
- การกลับจากรายละเอียดต้องรักษาคำค้น ตัวกรอง และตำแหน่งรายการเดิม
- เปลี่ยนหน้าเมื่อฟอร์มมีข้อมูลค้าง: เก็บ draft ในหน่วยความจำและให้กลับมาทำต่อ การเก็บข้อมูลลูกค้าบนอุปกรณ์ข้ามรอบใช้งานต้องกำหนดนโยบายก่อน

## 5. แนวทางภาพลักษณ์

ทิศทางที่ผู้ใช้กำหนด: **Crazsix Aurora** — ใช้แสงไล่สี mint/cyan/violet บนพื้น midnight navy ในโหมดมืด และพื้นขาวอมม่วงในโหมดสว่าง วางแสงหลัง shell/ส่วนหัว ใช้แผงข้อมูลและช่องกรอกพื้นทึบที่อ่านง่าย เส้นขอบละเอียดและมุมโค้ง แสงไม่ทับข้อความ ตาราง และตัวเลขสำคัญ ไม่ใช้แสงกะพริบหรือ animation วนซ้ำ

ทางเลือกโครงหน้าจอสำหรับดูประกอบ: **งานวันนี้** ใช้ sidebar และคิวงานเป็นศูนย์กลาง กับ **ตารางกระชับ** ใช้เมนูบนและแถวข้อมูลสำหรับคนที่ทำงานหลายรายการติดกัน ทั้งสองโครงใช้ Aurora เดียวกัน โดยเพิ่มปุ่มประวัติและแก้ไขต่อรายการ แนะนำใช้แนวแรกเป็น shell และยืมความกระชับของแนวที่สองมาใช้หน้าสต็อก/บัญชี

## 7. ทางเดินงานสำคัญ

### ขายสินค้าหนึ่งตัวเลือก — รุ่นแรก

1. ค้นหา/เลือกสินค้า → เลือกสี ไซส์ สภาพ ขนาดจริง → จำนวนและราคาขาย
2. เลือกรับเต็ม/ผ่อน → เงินที่รับจริงและวันครบกำหนดเมื่อผ่อน → ข้อมูลผู้รับ; “ค่าใช้จ่ายและการแบ่งเงิน” เปิดเพิ่มได้
3. ตรวจสอบสินค้า ยอดขาย เงินรับ หนี้ ต้นทุน ค่าส่ง/ค่ากลาง กำไรก่อนแอด และจำนวนหลังขาย → บันทึก
4. ผลสำเร็จมีเลขอ้างอิงและทางไป “รอส่ง” หรือ “ขายรายการถัดไป” ยืนยันด้วยผลบันทึกจริง

กลับขั้นก่อนได้โดยไม่ล้างข้อมูล สต็อกและ snapshot ต้องตรวจใหม่ก่อน commit ถ้าข้อมูลเปลี่ยน ให้ตรวจความต่างและยืนยันใหม่ ไม่เขียนทับหรือขายซ้ำเงียบ ๆ

### รับของเข้าร้าน

เลือกรายการรอรับ → กรอกจำนวนที่มาถึง/ต้นทุน/ค่าส่ง → แสดงยอดรวมและส่วนที่เหลือ → ยืนยันรับ → เปิดประวัติล็อตได้ การแก้ล็อตต้องแสดงผลต่อต้นทุนและรายจ่ายก่อนยืนยัน

### รับชำระเพิ่ม

เปิดคำสั่งซื้อ → เห็นยอดเต็ม/รับแล้ว/ค้างและประวัติ → กรอกจำนวนและวันที่ที่ระบบรองรับ → ตรวจยอดหลังรับ → บันทึกและกลับรายการเดิม ห้ามตีความว่าเป็นการเรียกเก็บหรือโอนเงินผ่านธนาคาร

### ส่งพัสดุและยกเลิก

ส่ง: เลือกรายการและจำนวนที่เหลือ → ใส่พัสดุและค่าส่งที่ยังไม่ลง → ตรวจส่วนแบ่ง → บันทึกส่ง

ยกเลิก: เปิดคำสั่งซื้อ → ตรวจว่าส่งไปหรือยัง → แสดงของที่จะคืนสต็อกและยอดคืนเงิน → ยืนยันตามข้อจำกัดธุรกิจ → ติดตามรอคืน/คืนเงินจริงจนจบ

### จองลูกค้า

รับจองและมัดจำ → บันทึกการจัดหา → พร้อมส่งมอบ → รับเงินครบและเลือกของจากสต็อก/จัดหาเฉพาะ → สรุปต้นทุนและค่าใช้จ่าย → ส่งมอบ สถานะจองและบัญชีต้องอัปเดตเป็นงานเดียวกันตามพฤติกรรมปัจจุบัน

## 8. สเปกหน้าจอหลัก

### วันนี้

ส่วนหัว: ช่วงเวลาชัดเจน + ปุ่มบันทึกขาย; สรุป 3 ค่า: ยอดขายที่รับรู้, เงินรับจริง, เงินสดสุทธิ โดยใช้ช่วงเดียวกันและแตะดูสูตรได้; คิวงานแยกรอส่ง/เกินนัด/รับเข้า; กราฟและรายการล่าสุดอยู่รองลงมา ไม่ใส่รายการสินค้าทั้งคลังซ้ำ

### สินค้า

ค้นหาเหนือรายการ มี chip สภาพ/มีของ/ใกล้หมดและตัวกรองขั้นสูง สรุป “ผลลัพธ์ที่แสดง” แยกจาก “ทั้งร้าน” แถวหนึ่งแสดงรูป ชื่อ สี/ไซส์/ขนาด สภาพ คงเหลือ และปุ่มขาย เมนูรองมีเติม/แก้ไข/ตรวจนับ/ประวัติ มือถือแปลงเป็นรายการซ้อนบรรทัดแทนย่อตารางจนอ่านไม่ได้

### คำสั่งซื้อ

มุมมองรวมแสดงป้ายชนิด “ขายปกติ / ผ่อน / จองลูกค้า” โดยไม่เปลี่ยนชนิดข้อมูลเดิม แยกแกนสถานะรับเงินและส่งของ เช่น “รับครบ · รอส่ง” หรือ “ค้าง ฿500 · ส่งแล้ว” รายละเอียดมีสินค้า เงิน พัสดุ และ timeline การเปลี่ยนแปลงที่ระบบมีหลักฐานจริง

### การเงิน

แท็บเงินสด/กำไร/รายงาน ใช้ date filter รูปแบบเดียวกัน ยอดเงินสดสุทธิ = เงินเข้า − เงินออก ไม่ใช้เป็นกำไร กำไรขายใช้วันที่ขาย/ส่งมอบและหักต้นทุนตามกติกาเดิม ค่าแอดและค่าใช้จ่ายร้านแสดงแยกให้เห็นว่าได้หักส่วนไหนแล้ว

### การตลาด

เครดิตกลางอยู่หัวหน้า ถัดมาเป็นแคมเปญและสถานะ บันทึกค่าแอดเปิดเป็นงานเฉพาะ แสดง “ประมาณการตามงบ” กับ “บันทึกยอดจริง” เป็นข้อความชัด รวมถึงผลต่อเครดิตและกำไร ไม่มีการแสดงราวกับเชื่อม Ads Manager สด

## 9. ข้อกำหนดร่วมทุกหน้า

- สถานะครบ: loading, empty ครั้งแรก, ค้นหาไม่พบ, validation error, offline, save failed, stale conflict, saved และยืนยันก่อนออกจาก draft
- error อยู่ใกล้ช่องพร้อมวิธีแก้ มี summary เมื่อหลายช่องผิด และไม่ปิดฟอร์มทิ้ง
- ปุ่มบันทึกมี busy state ป้องกันการส่งซ้ำ และสำเร็จเมื่อ server ยืนยันเท่านั้น
- ค่าระหว่าง render สดไม่ล้างฟอร์ม ไม่เปลี่ยนตัวเลือกที่ผู้ใช้กำลังแก้โดยไม่แจ้ง
- รายการยาวใช้ pagination หรือ progressive rendering หลังวัดปริมาณข้อมูล ไม่ render ฟอร์มขายของทุกสินค้าไว้พร้อมกัน
- วันที่แสดง พ.ศ. ตามภาษาไทยได้ แต่ค่าจัดเก็บ/คำนวณคงรูปแบบเดิมและใช้ Asia/Bangkok
- ข้อมูลเงินคงกติกาปัดเศษและกระจายสตางค์ ไม่ให้ UI เขียนสูตรใหม่คนละชุดกับ domain
- การกระทำย้อนกลับไม่ได้มี review ผลกระทบ; undo ใช้ได้เฉพาะกรณีที่มี compensating action ถูกต้องและไม่กระทบรายการต่อเนื่อง

เป้าหมาย accessibility: WCAG 2.2 AA พร้อมตรวจจริงก่อนประกาศว่าผ่าน ใช้ label เชื่อม input, keyboard และ focus ที่ไม่ถูกบัง, ข้อความไม่ใช้สีล้วน, contrast ข้อความปกติอย่างน้อย 4.5:1 ตามข้อยกเว้นมาตรฐาน กำหนดพื้นที่แตะของโครงการประมาณ 44×44 CSS px สำหรับงานบนมือถือ ไม่อ้างว่า 44px เป็นขั้นต่ำ AA ของ WCAG 2.2 ทุกกรณี

อ้างอิงมาตรฐาน: [W3C — How to Meet WCAG 2.2](https://www.w3.org/WAI/WCAG22/quickref/)

## 10. แนวทางพัฒนาและรักษาข้อมูลเดิม

ใช้ JavaScript modules ของเดิมเป็นฐาน UI ยังไม่มีเหตุผลจากการสำรวจนี้ที่ต้องย้าย framework ทั้งระบบ ข้อกำหนดประวัติทุกฟีเจอร์เพิ่มงานชั้นเขียนข้อมูลแบบมี revision และ audit event ที่ต้องบันทึกพร้อมธุรกรรม การคงสัญญาข้อมูลเดิมของ UI ไม่ได้แปลว่าฐานข้อมูลไม่ต้องเปลี่ยน ดู HISTORY-EDITING.md สำหรับขอบเขตข้อมูลและบริการเขียน

โครงสร้างเสนอ (ยังไม่ได้สร้าง):

```text
js/
  app.js                      จุดเริ่มและประกอบระบบ
  ui/shell.js                 เมนู, header, mobile navigation
  ui/components/              input, list, badge, drawer, review
  pages/                      today, inventory, receiving, orders, finance, marketing
  state/                      navigation, filter, draft และ selectors
  domain/                     กฎ stock/sale/payment/profit และ action เดิมที่ทยอยแยก
  history/                    query ประวัติ, diff, edit intent, impact preview
  mutations/                  คำสั่งเปลี่ยนข้อมูลที่คุม revision และ event เดียวกัน
  firebase-service.js         boundary อ่าน/เขียนและ conflict
css/
  tokens.css                  สี ตัวอักษร ระยะ theme
  components.css              ปุ่ม form table dialog
  pages.css                   layout เฉพาะหน้า
```

ลำดับแยก: tokens → shell/navigation → shared controls → render รายหน้า → event wiring → domain ที่ยังอยู่ใน app.js แยกเมื่อมี regression tests คุมแล้ว โมดูลเฉพาะทางเดิม เช่น ads, shipments, receiving-lots และ preorders ให้นำกลับใช้

`setupStockWorkspace()` ปัจจุบันผูกแผงตามตำแหน่ง `panels[0..4]` ควรแทนด้วย render ที่มีชื่อหรือ key เพื่อให้เปลี่ยน layout โดยไม่สลับฟอร์มผิด

ทุกไฟล์ browser ใหม่ต้องเพิ่มใน allowlist `scripts/build.js`; ตรวจว่ามีใน dist และไม่มี docs, tests หรือข้อมูลตัวอย่างหลุดไป deploy

### กติกาที่ต้องรักษา

| กรณี | สิ่งที่ห้ามเปลี่ยนโดยไม่ทำ migration/ทดสอบ |
|---|---|
| สินค้า | ID และความต่างสี/ไซส์/สภาพ/ขนาดจริง; ประวัติปรับยอด |
| ขาย | หักสต็อกครั้งเดียวและเชื่อมธุรกรรมที่เกี่ยวข้องครบ |
| เงิน | เงินรับจริงแยกจากยอดเต็ม/หนี้; คืนเงินมีประวัติ |
| จองลูกค้า | ไม่รับรู้เงินซ้ำเมื่อส่งมอบ; ต้นทุนที่ลงแล้วไม่ลงซ้ำ |
| จัดส่ง | ส่งบางส่วน/หลายรายการ; ค่าส่งเพิ่มและแก้ไขกระจายตรงยอด |
| แอด | เครดิตกลาง ยอดจริงแทนประมาณการ และประวัติวันที่มีผล |
| หลายเครื่อง | ตรวจ expected snapshot ต่อไป; conflict ไม่เขียนทับข้อมูลใหม่ |
| สำรอง | import/export ของเวอร์ชันเดิมที่ระบบรองรับต้อง round trip ได้ |

การเปลี่ยนเป็นหนึ่งเอกสารต่อรายการเป็นงานแยกหลังวัดขนาดเอกสาร/จำนวนรายการ/ความถี่ conflict และออกแบบ migration, idempotency, rollback จนชัด ไม่ผูกเป็นเงื่อนไขบังคับของการเปลี่ยน UI รุ่นแรก

## 11. Roadmap และลำดับส่งมอบ

ประมาณการปรับตามขอบเขตใหม่ 10–14 สัปดาห์สำหรับผู้พัฒนาเต็มเวลา 1 คนและรอบ feedback ของเจ้าของร้านที่สม่ำเสมอ เป็นช่วงประมาณเพื่อวางลำดับ ไม่ใช่กำหนดส่งที่ยืนยันแล้ว ยังไม่รวมย้ายฐานข้อมูล ตะกร้าหลายสินค้า และ API ขนส่ง/AI ภายนอก

| ระยะ | เวลาโดยประมาณ | งานส่งมอบ | เงื่อนไขก่อนผ่าน |
|---|---|---|---|
| A: ตรึงทิศทาง | 3–5 วัน | ทดลอง prototype, เดิน 5 งานจริง, glossary ตัวเลข, baseline | เจ้าของร้านยืนยันเมนูและกติกาเงิน; ได้เวลา/จุดติดขัดฐาน |
| B: Aurora และฐานประวัติ | 3–4 สัปดาห์ | tokens, shell, navigation, controls, สถานะฟอร์ม, mutation/revision/audit, ข้อมูลตั้งต้น | responsive/theme ผ่าน; แก้ข้อมูลและประวัติสำเร็จ/ล้มเหลวพร้อมกัน; route เดิมเปิดได้ |
| C: งานขายประจำวัน | 2–2.5 สัปดาห์ | วันนี้ สินค้า ฟอร์มขาย คำสั่งซื้อ รอส่ง รับเงิน | ขาย→ผ่อน→ส่ง/ยกเลิกครบ; สต็อก/บัญชีตรง |
| D: รับเข้าและจอง | 1–1.5 สัปดาห์ | รับเข้า/รับบางส่วน/ล็อต/ตรวจนับ/จองลูกค้า | ต้นทุนเฉลี่ยและการรับรู้เงินไม่ซ้ำ |
| E: เงินและการตลาด | 1–1.5 สัปดาห์ | การเงิน รายงาน เครดิต/แอด เครื่องมือข้อมูล | สูตรและ drilldown/CSV ตรง; แอดจริง/ประมาณการชัด |
| F: ตรวจและเปิดใช้ | 1–1.5 สัปดาห์ | UAT มือถือ/คอม, regression, accessibility, สิทธิ์, rollout | เกณฑ์ release ผ่านและมีข้อมูลสำรอง/แผนกลับรุ่น |

HIST-01/02 ต้องเสร็จก่อนปล่อยฟีเจอร์ที่แก้ข้อมูลรุ่นใหม่ ทุกงานรายโมดูลต้องผ่าน HIST-03/04 ด้วย ไม่เลื่อนประวัติไปทำหลังเปิดใช้รุ่นใหม่

งานสิทธิ์เริ่มกำหนดใน A และพัฒนาควบคู่ B–E โดยประเมินเวลาเพิ่มตามวิธีเข้าสู่ระบบและจำนวนบทบาท ก่อนเปิดใช้วงกว้างต้องทดสอบ deny/allow จริงฝั่ง rules

## 12. การทดสอบและเกณฑ์เปิดใช้

ฐานเดิมมี Playwright พร้อมฐานข้อมูลจำลอง ให้ปรับ selectors ที่ผูก layout ไปใช้ role/label หรือ domain ID เท่าที่เหมาะสม ห้ามลบ assertion ด้านยอดเงินเพื่อให้ UI ใหม่ผ่านง่ายขึ้น

- ใช้ชุดเดิม: store, inventory-management, stock-options, measurements, receiving-lots, preorders, shipments, shipment-allocation, shipment-cost, cancel-sale, cancel-accounting, profit, personal-profit, ads-*, firestore-service, store-tools และ theme
- เพิ่มเมื่อ implementation เกิดขึ้น: route/back/refresh, กลับขั้นและ draft, review ก่อนขาย, คงตัวกรองหลังเปิดรายละเอียด, คิวงานไปถึงรายการ, keyboard ทุกทางเดินงาน และ UI mobile ที่มีข้อมูลยาว
- fixture ครอบคลุมไม่มีข้อมูล/รายการน้อย/หลายร้อยตัวเลือก/ชื่อยาว/หลายขนาด/ผ่อนค้าง/คืนเงินค้าง/แอดประมาณการ/ข้อมูลเก่า
- ตรวจประวัติ: ทุกการเพิ่ม/แก้/ยกเลิก/คืนค่า มี event และ revision ตรงกัน, ล้มเหลวแล้วไม่มี event ลอย, แก้รายการเกินหนึ่งปี/ปิดแล้ว/เก็บถาวรมีช่องทางปรับปรุง, restore สร้าง revision ใหม่ไม่ลบรายการภายหลัง, backup/import คงประวัติ, ค้นหาประวัติข้ามหน้าได้
- ตรวจหลายเครื่อง: ขายตัดสต็อกพร้อมกัน รับเงินพร้อมกัน เปลี่ยนราคาขณะมี draft แล้วต้องไม่เขียนทับ
- ทำ `npm test` และ `npm run build`; ตรวจ browser assets ใน dist ตาม allowlist และไม่มี console error บนเส้นทางหลัก
- ทดสอบมือถือ 360 และ 390px, tablet 768px, desktop 1024 และ 1440px รวมข้อความไทยยาว, ซูม 200%, แป้นพิมพ์ และ light/dark
- ตรวจ theme contrast และ screen reader ของปุ่ม/ช่องกรอก/ข้อความบันทึก มี focus คืนจุดเดิมหลังปิด dialog
- ทำ UAT 5 งานกับเจ้าของร้าน: ขายรับเต็ม, ขายผ่อนแล้วรับเพิ่ม, รับบางส่วน, รวมพัสดุ, ตรวจเงินสดเทียบกำไร

เป้าหมายที่เสนอหลังเก็บ baseline: เวลาขายหนึ่งตัวเลือกที่ลูกค้าจ่ายเต็มลดอย่างน้อย 30%, ผู้ใช้ทำ 5 งานหลักสำเร็จโดยไม่ต้องช่วยอย่างน้อย 90% ในรอบทดสอบ, ความคลาดเคลื่อนสต็อก/เงินจาก regression เป็นศูนย์ และไม่มี draft หายเมื่อ retry เป้าหมายเหล่านี้ยังไม่ได้วัดหรือรับรองผล

ด้านความเร็ว: วัดเวลาเปิดหน้าจาก cache, สลับหน้า และ render รายการบนอุปกรณ์เป้าหมายพร้อมจำนวนข้อมูลจริงที่จำลองก่อนตั้ง budget; ไม่อ้างว่าการเปลี่ยนสี/แยกไฟล์ทำให้เร็วขึ้นโดยไม่มีการวัด

## 13. แผนเปลี่ยนผ่าน

1. สำรองข้อมูลและทดสอบ restore ในสภาพแวดล้อมแยก เก็บยอดควบคุม จำนวน และ ID ก่อนเปลี่ยน
2. พัฒนา UI บนฐานข้อมูลจำลอง/โครงการทดสอบ ใช้กฎธุรกิจและ format สำรองเดิมในรุ่นแรก
3. ทดลองกับเจ้าของร้านบน preview ที่ตั้งค่าฐานข้อมูลทดสอบชัดเจน URL preview เพียงอย่างเดียวไม่ทำให้แยกข้อมูล production
4. เปิดใช้เป็นชุดหน้าที่ทำงานต่อกันครบ เช่น สินค้า→ขาย→คำสั่งซื้อ→รับเงิน→ส่ง โดยไม่ปล่อยสถานะค้างกลางทาง
5. ตรวจยอดควบคุมก่อนและหลังเปิดใช้ หาก UI มีปัญหาให้กลับโค้ดรุ่นก่อนที่ยังรองรับ format เดิม ไม่ restore ข้อมูลเก่าทับธุรกรรมใหม่
6. งาน migration ในอนาคตต้องมีแผน compatibility/rollback ของข้อมูลแยกต่างหาก

## 14. การตัดสินใจที่ต้องได้ก่อนเริ่มระยะ B

สมมติฐานเริ่มต้นที่ใช้ในข้อเสนอนี้: dark เป็นค่าเริ่มต้น มี light; เน้นเจ้าของร้านหนึ่งคนก่อน; ขายหนึ่งตัวเลือกต่อการบันทึกใน MVP; สไตล์ Aurora ตามคำขอ; โครงหน้า “งานวันนี้” เป็นทิศทางหลัก; ประวัติและแก้ไขทุกฟีเจอร์เป็น P0

- ปรับระดับแสง Aurora และความแน่นของข้อมูลตามที่ถนัด โดยคงสไตล์ที่ผู้ใช้เลือกแล้ว
- ยืนยัน 3 งานที่ใช้บ่อยที่สุดและอุปกรณ์หลัก เพื่อจัดลำดับงานจริง
- ยืนยันคำเรียกเงินสด/กำไรและกติกาการแบ่งเงินที่ต้องคง
- ระบุผู้ใช้งานและสิทธิ์ที่ต้องมี เพื่อวางการเข้าถึงก่อนขยายใช้
- เลือกชุดแรกที่เริ่มพัฒนา: แนะนำ UI foundation + สินค้า + ขาย + คำสั่งซื้อ ก่อนรับเข้า/การเงิน/การตลาด

- เก็บภาพฐาน desktop/mobile แล้ว
- จัดทำแผน เมนูใหม่ สเปกฟีเจอร์ backlog เกณฑ์ตรวจรับ และแผนเปลี่ยนผ่านแล้ว
- ปรับเป็น Crazsix Aurora และเพิ่มสเปกประวัติ/แก้ย้อนหลังทุกฟีเจอร์ตามคำขอ พร้อมยกระดับงานนี้เป็น P0 แล้ว
- แนวหน้าจอประกอบใช้ข้อมูลสมมติและแสดงเพียงบางทางเดินงาน ไม่ใช่ฟีเจอร์ production ที่พัฒนาเสร็จ
- ยังไม่ได้รัน regression suite ทั้งระบบ เพราะรอบนี้ไม่ได้แก้ runtime ของแอป ผลทดสอบแนวหน้าจอให้ดู `PREVIEW-QA.md`
