# ผลตรวจแนวหน้าจอและขอบเขตงาน

## ฉบับล่าสุด — Aurora Workspace 3 (18 ตุลาคม 2569)

ฉบับนี้แทนแนวหน้าจอเก่า: มีกราฟยอดขาย/รับเงิน/กำไร กราฟเงินรับ–จ่าย รายการรอส่งที่บันทึกได้ แบ่งเงินรายออเดอร์และหลังส่ง พร้อม 12 พื้นที่ทำงาน ข้อมูลเป็นชุดสมมติ ณ 17 ตุลาคม 2569 ในหน่วยความจำ ไม่เชื่อม Firestore

### พฤติกรรมที่ตรวจผ่านด้วย Chromium

- ช่วงเวลา 7 วัน/เดือนนี้เปลี่ยนข้อมูลกราฟและยอดรวม
- ขาย 2 × 390 รับมัดจำ 300 ส่วนตัว 10% เก็บแอด 35/ชิ้น: แสดงขาย 780 ค้าง 480 ส่วนตัว 78 แอด 70
- ส่งบางส่วน 1 ชิ้น: แบ่งส่วนตัว 39 แอด 35 และเหลือรอส่ง 1 ชิ้น สต็อกไม่ลดซ้ำ
- รับค่างวดเพิ่ม 480 แล้วแก้ราคาเป็น 410/ชิ้น: เงินรับยัง 780 ยอดค้างใหม่ 40
- แก้ค่าส่งพัสดุ 25 → 40 และเลขติดตาม: ปรับรายการจ่ายเดิมหนึ่งรายการ
- ยกเลิกบันทึกส่ง: จำนวนกลับรอส่ง ไม่คืนสต็อก และค่าส่งยังอยู่
- ปฏิเสธการรวมออเดอร์คนละผู้รับในพัสดุเดียว
- รับเข้าล็อตอีก 3 ชิ้น: ยอดรับจาก 20 เป็น 23 และคงเหลือเพิ่ม 3
- พรีออเดอร์รับมัดจำจนครบ → ของพร้อม → ยืนยันขาย: เชื่อมเงินรับเดิม 890 โดยไม่รับเงินซ้ำ
- ถอนใช้ส่วนตัวสร้างรายการเงินจริงและประวัติ
- แก้ชื่อสินค้า แล้วย้อนใช้ชื่อก่อนหน้า: สร้างฉบับใหม่และยังเห็นเหตุผลของฉบับก่อน
- ยกเลิกขายก่อนส่งแล้วคืนเงินจริง: บังคับเหตุผล ยอดรอคืนเป็นศูนย์และไม่มีปุ่มคืนซ้ำ
- ดู CSV ตามช่วงเวลาและเลือกคัดลอกข้อความได้ ไม่อ้างว่าดาวน์โหลดไฟล์จากหน้าตัวอย่างนี้
- แบ่งหน้าตาราง 8 รายการ ปุ่มก่อนหน้า/ถัดไปทำงาน
- เมนูมือถือเพิ่มเติมเปิดหน้าสต็อกได้ หน้าตรวจ/แก้ไขวางในลำดับหน้าเพื่อให้มองเห็นในกรอบตัวอย่าง ปิดด้วย Escape ได้

### ตรวจการจัดวาง

ตรวจ 12 หน้า × ความกว้างเนื้อหา 1024/736/358/320px × สว่าง/มืด รวม 96 กรณี ไม่พบแอปล้นแนวนอนและไม่พบ JavaScript page error ในชุดทดสอบนี้ ตารางที่กว้างเลื่อนได้ภายในพื้นที่ของตัวเอง

ตรวจช่องแก้ไขบนความกว้าง 320px เพิ่ม และตรวจกราฟสองหน้า สองช่วงเวลา สี่ความกว้างโดยเทียบขอบเขตตัวอักษรแกน เพื่อแก้วันที่และหน่วยที่ชิดกัน

### ขอบเขตการตรวจ

ตรวจต้นแบบและการคำนวณจำลอง ไม่ใช่ production regression หรือการรับรองบัญชี ยังไม่ได้ทดสอบ screen reader เต็มรูปแบบ อุปกรณ์สัมผัสจริง การทำงานหลายเครื่อง audit ถาวร สิทธิ์ผู้ใช้ หรือการย้ายข้อมูล การโหลดตัวอย่างใหม่ล้างรายการทดลอง ยังไม่เปลี่ยน runtime ของแอป ไม่ deploy และไม่เขียนข้อมูลร้าน

ผลตรวจฉบับก่อนด้านล่างเก็บเป็นประวัติ ไม่ใช่หลักฐานของหน้าตัวอย่างล่าสุด

วันที่ 17 ตุลาคม 2569

## ฉบับปรับปรุง — Crazsix Aurora + ประวัติ/แก้ไข

ปรับสไตล์เป็น midnight navy พร้อมแสง mint/cyan/violet และเพิ่มประวัติรวมร้าน ทางลัดประวัติแต่ละฟีเจอร์ ค่าเดิม/ค่าใหม่ เวอร์ชัน เหตุผล และหน้าตรวจผลกระทบก่อนแก้ไข

ตรวจตัวอย่างแก้ไข 12 ชนิดในหน่วยความจำ: การขาย ราคาสินค้า รับเงิน สั่งเข้าร้าน พัสดุ จองลูกค้า รายจ่าย งบแคมเปญ หมายเหตุเติมเครดิต ข้อมูลร้าน เหตุผลตรวจนับ และคำอธิบายไฟล์สำรอง ทั้งหมดสร้างเวอร์ชันใหม่และเหตุผลในหน้าประวัติได้

กรณีสำคัญที่ตรวจแล้ว:

- บังคับระบุเหตุผลก่อนตรวจผลการแก้ไข
- เปลี่ยนราคาขาย 390 → 410 บาท จำนวน 2 ชิ้น: ยอดขาย 820 เงินรับจริงยัง 780 และยอดค้าง 40 บาท
- หลังยืนยัน หน้าสรุปยอดขายในข้อมูลตัวอย่างเปลี่ยนเป็น 1,410 บาท (820 + การขายอีก 590)
- ใช้ค่าจากเวอร์ชันแรกแล้วสร้างเวอร์ชันที่สาม โดยเวอร์ชันที่สองยังอยู่
- ลดขายจาก 2 เป็น 1 ชิ้น: สต็อกจาก 8 เป็น 9 และมีรอคืนเงิน 390 บาท ไม่ถือว่าคืนเงินจริงแล้ว
- ค้นหาที่ไม่มีผลลัพธ์และกรองประวัติการเงินทำงาน
- เมนูมือถือ “เพิ่มเติม → ประวัติทั้งหมด” ใช้ได้ และเปิดหน้าตรวจผลก่อนแก้บนมือถือได้

ตรวจ layout สองแบบ × 8 หน้า × 5 ความกว้าง (320/360/390/768/1024px) × 2 โหมดสี รวม 160 กรณี ไม่พบการล้นแนวนอนของแอปหรือปุ่ม/ช่องกรอก/แผงเนื้อหาที่ตรวจ และไม่พบ JavaScript page error ความสูงเริ่มต้นของสองแบบเท่ากันในแต่ละ breakpoint

ภาพล่าสุด: [Aurora desktop](aurora-desktop.png), [ประวัติทั้งหมด](aurora-history.png), [ตรวจผลก่อนแก้ไข](aurora-edit-review.png), [ประวัติมือถือ](aurora-history-mobile.png), [ตรวจผลบนมือถือ](aurora-edit-mobile.png)

ขอบเขต: เป็น prototype ในบทสนทนา ใช้ข้อมูลสมมติในหน่วยความจำ การแก้จะไม่คงอยู่หลังโหลดใหม่และไม่เขียนฐานข้อมูลจริง ตัวอย่างแต่ละชนิดแสดงเพียงบางช่องที่แก้ได้ ไม่ใช่ implementation ครบทุกช่อง/ทุก dependency ใน [สเปกประวัติ](HISTORY-EDITING.md) ยังต้องพัฒนา auth, atomic audit, ประวัติถาวร, server validation และการคำนวณครบทุกความสัมพันธ์ตามแผน

ผลตรวจฉบับแรกด้านล่างเก็บไว้เป็นฐานอ้างอิง ไม่ใช่ผลตรวจ production ของ Aurora

## แอปปัจจุบัน

เปิดหน้า home, stock, sell, ads, shipments, preorder, tx, profit, report และ tasks ผ่าน Chromium ด้วย `boot()` ใน `tests/helpers.js` ซึ่งแทน Firebase ด้วยฐานข้อมูลจำลองและบล็อกคำขอภายนอก พบ JavaScript page error 0 รายการกับข้อมูลชุดนี้

เก็บภาพ desktop 1440×1000 และหน้าขาย mobile 390×844 หน้าขายมีความกว้างเอกสาร 390px เท่ากับ viewport ในกรณีที่สำรวจ ไม่ใช่การรับรองทุกหน้าหรือทุกขนาดข้อมูล

## แนวหน้าจอฉบับแรก — Crazsix Studio (ก่อนคำขอ Aurora)

ตรวจ fragment ที่แสดงในบทสนทนาด้วย renderer ของสกิล visualize และ Chromium ใน iframe พร้อม runtime เดียวกับแนวแสดงผล ไม่เชื่อม Firebase หรือบริการโฆษณา

ตรวจพฤติกรรม:

- กดงานรอส่งจากหน้าแรกแล้วได้ 2 รายการตามข้อมูลตัวอย่าง
- ค้นหาสินค้าที่ไม่มีแล้วแสดงสถานะไม่พบ
- กรองใกล้หมดแล้วได้ 2 ตัวเลือกตามเกณฑ์ที่แสดง
- กรอกขายเกินสต็อกแล้วมี error ในฟอร์ม
- ตัวอย่างขาย 2 ชิ้น ราคา 390 รับมัดจำ 300 แสดงหนี้ 480 และสต็อกหลังขาย 6 ชิ้น
- ย้อนจากหน้าตรวจสอบแล้วข้อมูลลูกค้าและมัดจำยังอยู่
- ยืนยันตัวอย่างแล้วมีผลจำลองและทางไปคำสั่งซื้อ โดยไม่เปลี่ยนสต็อก/เงินในข้อมูลตัวอย่าง
- เปิดรายละเอียดและปิดด้วย Escape
- สลับแนว “งานวันนี้” และ “ตารางกระชับ” ผ่านตัวควบคุมสลับแบบ
- เมนูมือถือ “เพิ่มเติม” เปิดไปการเงินได้ และปุ่มขายเปิดฟอร์มได้

ตรวจ layout ของทั้งสองแบบ ทุกเมนู 7 หน้า ที่ความกว้างภายใน 320, 360, 390, 768 และ 1024px ในโหมดสว่างและมืด รวม 140 กรณี ไม่พบความกว้างเนื้อหาเกินแอปหรือช่องกรอก/ปุ่ม/แผงเนื้อหาล้นกรอบแนวนอนจากการตรวจ bounding box พบ JavaScript page error 0 รายการ

ผลตรวจนี้ไม่ได้ครอบคลุม screen reader, contrast ทุกคู่สี, touch บนอุปกรณ์จริง หรือการบันทึกข้อมูล production ต้องตรวจสิ่งเหล่านี้เมื่อพัฒนา UI จริง

## สิ่งที่เปลี่ยนใน repository

เพิ่มเฉพาะแผน ผลตรวจ และภาพอ้างอิงใน `docs/ux-overhaul/` ไม่แก้ runtime, dependency, build config หรือ Firestore rules รอบนี้จึงไม่ได้รัน regression suite ของแอปทั้งระบบและไม่ได้ deploy

แผนและภาพใน docs ไม่อยู่ใน allowlist ของ `scripts/build.js` จึงไม่ถูกรวมใน public build ปัจจุบัน

## ข้อจำกัดของแนวหน้าจอ

- ตัวเลข ชื่อสินค้าและลูกค้าเป็นข้อมูลสมมติสำหรับแสดงลำดับและความหมายของยอด
- แสดง 7 พื้นที่หลักและขั้นตอนขายแบบย่อ ไม่ได้ทำทุกฟอร์มตาม backlog
- รับเข้า แอด และนำเข้า แสดงโครงข้อมูล/แนวขั้นตอน ไม่ได้สร้างธุรกรรม
- รูปแบบเมนูมือถือในแนวหน้าจออยู่ตามลำดับเนื้อหา; การวางแถบคงที่และพื้นที่คีย์บอร์ดบนอุปกรณ์จริงเป็นส่วนของ implementation
- ค่าส่ง ค่ากลาง และเงินแบ่งในตัวอย่างขายเป็น 0; ฟอร์มขั้นสูงและการคำนวณเต็มอยู่ในแผนพัฒนา
- แบบตารางกระชับใช้การจัดเมนูและระยะรายการที่ต่างกัน เป็นทางเลือกเพื่อเทียบรูปแบบ ไม่ใช่ผลิตภัณฑ์อีกชุด
- ไม่มีการประเมินเวลางานจริงหรือความพึงพอใจกับผู้ใช้แล้ว ตัวเลขเป้าหมายในแผนเป็นเกณฑ์ที่เสนอ
