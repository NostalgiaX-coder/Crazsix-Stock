# Crazsix Aurora — ประวัติและแก้ไขทุกฟีเจอร์

วันที่ 17 ตุลาคม 2569 · ข้อกำหนด P0 ตามคำขอผู้ใช้ · สเปกก่อนพัฒนา

## 1. ความหมายของ “มีประวัติและแก้ไขได้ตลอดเวลา”

ทุกฟีเจอร์ที่บันทึกหรือเปลี่ยนข้อมูลร้านต้องเปิดรายการย้อนหลัง ดูข้อมูลก่อน/หลัง และเริ่มแก้ไขได้ ไม่กำหนดว่ารายการเก่ากี่วันแล้วห้ามแก้ รวมรายการส่งแล้ว รับเงินครบ ปิดแคมเปญ หรือเก็บถาวร ผู้ใช้ที่มีสิทธิ์ยังเข้าไปแก้หรือสร้างรายการปรับปรุงที่เกี่ยวข้องได้

ข้อมูลทั่วไปแก้เป็นเวอร์ชันใหม่ได้โดยตรง ส่วนยอดเงิน จำนวน ต้นทุน และสถานะที่มีผลกับรายการอื่น ต้องแสดงผลกระทบและสร้างการปรับปรุงที่รักษาสมดุลของรายการทั้งหมด ปุ่ม “แก้ไข” ต้องพาไปจนจบงาน ไม่ใช่พาไปข้อความว่าแก้ไม่ได้โดยไม่มีทางเลือก

ประวัติแต่ละเวอร์ชันเป็นหลักฐานที่คงไว้ การแก้ข้อมูลปัจจุบันไม่เขียนทับประวัติเก่า การเลือก “ใช้ค่าจากเวอร์ชันนี้” สร้างเวอร์ชันใหม่ ณ ปัจจุบันและตรวจผลกระทบต่อรายการที่เกิดภายหลัง

การแก้บันทึกโอน/คืนเงิน/ส่งพัสดุในแอปไม่ได้โอนเงินหรือย้อนเหตุการณ์จริงของธนาคารและขนส่ง ต้องบันทึกยอดจริง/วันที่จริงหรือสร้างงานที่รอดำเนินการตามข้อเท็จจริง

การค้นหา กรอง เรียงรายการ และเปิดหน้าจอไม่ต้องสร้างประวัติธุรกิจทุกคลิก การตั้งค่าร้าน สิทธิ์ และการนำเข้า/ส่งออกเป็นเหตุการณ์ที่มีประวัติ ส่วน theme ส่วนตัวเก็บเป็น preference ของผู้ใช้แยกจากบัญชีร้าน

## 2. UX มาตรฐานทุกฟีเจอร์

แต่ละรายการมีทางเข้าคงที่: **รายละเอียด · ประวัติ · แก้ไข** ใช้รูปแบบเดียวกันบนคอมพิวเตอร์และมือถือ

หน้าประวัติรายรายการแสดง:

- วันเวลาที่บันทึกตามเวลาไทย และวันที่รายการมีผล หากต่างกัน
- ผู้ทำรายการ/ระบบอัตโนมัติ และชนิดงาน: สร้าง แก้ไข ปรับปรุง ยกเลิก เก็บถาวร คืนค่า นำเข้า
- เวอร์ชัน ค่าเดิม → ค่าใหม่ พร้อมหน่วย จำนวน และสกุลเงิน
- เหตุผลที่แก้ โดยบังคับในรายการที่กระทบเงิน/สต็อก/สถานะสำคัญ
- รายการที่เชื่อมโยง เช่น ขาย → ชำระเงิน → พัสดุ → รายจ่าย → รายงาน
- ปุ่ม “เปิดรายการปัจจุบัน”, “แก้ไขจากข้อมูลล่าสุด” และ “ใช้ค่าจากเวอร์ชันนี้” เมื่อมีความหมายสำหรับข้อมูลนั้น

“ประวัติทั้งหมด” รวมทั้งร้าน ค้นด้วยชื่อ รหัส ลูกค้า หรือเหตุผล และกรองฟีเจอร์ ช่วงวัน ผู้ทำ ชนิดกิจกรรม รายการเก็บถาวรได้ แบ่งหน้าและค้นบนข้อมูลประวัติทั้งหมด ไม่ใช่ค้นเฉพาะหน้าที่โหลดมาแล้ว

ในฟีเจอร์แต่ละหน้ามีทางลัดประวัติของฟีเจอร์นั้น พร้อมตัวกรองเดิม เมื่อกลับจากแก้ไขต้องคงจุดที่ทำงานไว้

## 3. ตารางความครอบคลุมและการแก้ไข

|---|---|---|---|
| สินค้า/ตัวเลือก/รูป | เพิ่ม เปลี่ยนชื่อ/สี/ไซส์/สภาพ/ขนาด ราคา รูป เก็บถาวร รวมซ้ำ | ข้อมูลและราคาอ้างอิงปัจจุบัน พร้อมประวัติรูปที่กู้ได้ตามนโยบายเก็บไฟล์ | ชื่อ/รูปปัจจุบันไม่ทับ snapshot ของรายการขายเก่า; ตรวจตัวเลือกซ้ำ |
| เพิ่ม/เติมสต็อก | แต่ละรอบเข้า จำนวน ต้นทุน ค่าส่ง รายจ่าย และการแก้ | จำนวน ต้นทุน วันที่ ค่าส่งและคำอธิบาย | ตรวจของที่ขาย/ส่งแล้ว คำนวณส่วนที่ยังเหลือและส่วนปรับปรุงตามนโยบายต้นทุน |
| สั่งซื้อรอรับ | สร้าง/แก้/ยกเลิก/รับบางส่วน | สินค้า จำนวน ต้นทุน วันและหมายเหตุ | ไม่ลดจำนวนสั่งต่ำกว่ารับแล้วโดยเงียบ ๆ; มีทางแก้ล็อต/คืนผู้ขาย/ปรับปรุงที่เชื่อมกัน |
| ล็อตรับของ | รับแต่ละครั้ง การแบ่งค่าส่ง ต้นทุนเฉลี่ย รายจ่าย | จำนวนจริง ต้นทุนจริง วันรับ ค่าส่ง | ปรับล็อต สต็อก และบัญชีในคำสั่งเดียว; ไม่สร้างของซ้ำ |
| ตรวจนับ | ยอดระบบ ยอดนับ ผลต่าง เหตุผล และการแก้ | เหตุผลหรือแก้ยอดนับผ่าน revision ใหม่ | ใช้ผลต่างจากสถานะล่าสุด ไม่ย้อนทับของที่ขายหลังตรวจนับ |
| การขาย | สินค้า ตัวเลือก จำนวน ราคาขาย ค่าใช้จ่าย ผู้รับ แคมเปญ เงินแบ่ง | ทุกช่องที่ผู้ใช้บันทึก รวมขายเสร็จแล้วผ่านขั้นตอนปรับปรุง | ตรวจเงินรับ/ส่งแล้ว/คืนแล้ว, หนี้เพิ่ม/รอคืนเงิน, stock delta และกำไร |
| รับเงิน/มัดจำ/ผ่อน | แต่ละครั้งของเงินรับ วันที่ จำนวน แหล่งชำระ หมายเหตุ | แก้ข้อมูลหรือปรับยอดรับที่ลงผิด | ไม่แก้ยอดขายแทนเงินรับ; แสดงหนี้หรือรอคืน/รับเพิ่มตามจริง ไม่เติมเงินรับอัตโนมัติ |
| จองลูกค้า | ข้อมูลจอง การจัดหา รับเงิน ส่งมอบ ยกเลิก | ลูกค้า สินค้า ราคา จำนวน วันนัด และข้อมูลต้นทุน/ส่งมอบ | หากส่งมอบแล้วเชื่อมแก้การขาย/เงิน/สต็อก; ไม่กลับไปรับรู้รายได้หรือหักของซ้ำ |
| จัดส่ง/พัสดุ | จำนวนต่อคำสั่งซื้อ ผู้รับ ขนส่ง tracking ค่าส่ง แก้/ยกเลิกส่ง | ผู้รับ เลขพัสดุ ขนส่ง จำนวนและค่าส่งที่ลงผิด | บันทึกส่ง/คืนสินค้า/แก้การจัดสรรตามจริง ไม่ตีความว่าแก้ในระบบแล้วของย้อนกลับ |
| ยกเลิก/คืนเงิน | สาเหตุ ยอดรับ ยอดต้องคืน คืนเงินจริง คืนสต็อก | รายละเอียด และแก้ยอด/สถานะคืนผ่านรายการปรับปรุง | ไม่คืนสต็อกหรือเงินซ้ำ; ยอดคืนไม่เกินเงินรับสุทธิที่พิสูจน์ได้ |

| ค่าแอดจริง/อัตโนมัติ | วันที่ แหล่งยอด ค่าเดิม/ใหม่ การแทนที่ประมาณการ ส่วนแบ่ง | แก้ยอดจริง วันที่ แหล่งเครดิตและการกระจาย | reconcile ยอดอัตโนมัติ/เครดิต/บัญชี ไม่หักซ้ำ และไม่แก้ historical allocation เงียบ ๆ |

| ตั้งค่า/ผู้ใช้/สิทธิ์ | เปลี่ยนค่าร้าน เพิ่ม/เปลี่ยนสิทธิ์ ถอนสิทธิ์ | ผู้มีสิทธิ์แก้และย้อนตั้งค่าได้ | ตรวจสิทธิ์ฝั่งบริการทุกครั้ง ไม่ให้การคืนค่าเพิ่มสิทธิ์ที่ผู้ทำไม่มี |

## 4. ตัวอย่างแก้การขายที่รับเงินแล้ว

ขาย 2 ชิ้น × 390 = 780 บาท รับจริง 780 บาท สต็อกปัจจุบัน 8 ชิ้น และยังไม่ส่งสินค้า

- เปลี่ยนราคาต่อชิ้นเป็น 410: ยอดขายใหม่ 820 เงินรับจริงยัง 780 หนี้เพิ่ม 40 สต็อกยัง 8 ต้องติดตามรับเงินเพิ่ม
- เปลี่ยนเป็น 1 ชิ้น × 390: คืนจำนวนในระบบ 1 ชิ้น สต็อกเป็น 9 ยอดขายใหม่ 390 รับจริงยัง 780 จึงมีรอคืนเงิน 390 การบันทึกแก้ยังไม่ถือว่าคืนเงินจริงแล้ว
- หากส่งออกไปแล้ว จำนวนที่เอาออกต้องเข้าสู่ทางคืนสินค้า/แก้รายการพัสดุตามสถานะจริง ไม่คืนสต็อกทันทีที่แก้จำนวนขาย
- หากแก้ต้นทุนล็อตที่เคยขายแล้ว ต้องให้เลือกวิธีมีผลที่กำหนดไว้: ปรับเฉพาะต้นทุนคงเหลือ หรือปรับต้นทุนขายย้อนหลังแบบมี revision และสรุปรายงานที่เปลี่ยน ห้ามเลือกวิธีให้เองโดยไม่แสดงผล

ทุกครั้งแสดง diff → ผลต่อสต็อก/เงินรับ/หนี้/คืนเงิน/กำไร/รายงาน → เหตุผล → ยืนยัน → บันทึกข้อมูลและประวัติพร้อมกัน

## 5. สัญญาข้อมูลและการบันทึก

โครงสร้างเสนอเพื่อประเมินก่อน implementation:

```text
record:
  id, revision, updatedAt, archivedAt?

history event:
  eventId, operationId, storeId, actorUid/actorKind
  entityType, entityId, entityRevisionBefore, entityRevisionAfter
  action, recordedAt(server), effectiveDate(Asia/Bangkok)
  changedFields, beforeValues, afterValues, reason
  relatedRefs, impacts, restoredFromEventId?, sourceImportId?
```

- ใช้ event แยกเอกสาร เช่น `stores/{storeId}/history/{eventId}` และมี index/แบ่งหน้า ไม่เพิ่มอาร์เรย์ประวัติไม่จำกัดลงในเอกสารข้อมูล 7 ชนิดเดิม
- งานที่แก้หลาย entity ใช้ operation เดียวผูก event ราย entity หรือ envelope ที่ตรวจ revision ทุก entity ได้ บันทึก record, ผลที่เกี่ยวข้อง และ event แบบ atomic
- ใช้ operationId สำหรับ idempotency: retry คำสั่งเดิมไม่สร้างธุรกรรมหรือ event ซ้ำ; คำสั่งใหม่อ้าง revision ล่าสุดเท่านั้น
- อ่านรายการและ dependency ล่าสุด ตรวจสิทธิ์ ตรวจ revision คำนวณผล แล้วจึง commit; conflict ต้องนำข้อมูลผู้ใช้กลับมาตรวจเทียบกับล่าสุด
- recordedAt และผู้ทำมาจากบริการที่เชื่อถือได้ ตรวจผู้ใช้จาก authentication ไม่เชื่อ actor/time ที่ browser หรือไฟล์นำเข้าส่งมาเอง
- ห้ามเปิดสิทธิ์ให้ client แก้/ลบ audit event ที่ commit แล้ว ออกแบบบริการเขียน/กฎให้บังคับว่าการแก้ธุรกิจและ audit เป็น operation เดียวกัน
- คำสั่งเก่าทุกจุดที่ยังเขียนตรงต้องย้ายเข้าสู่ boundary เดียวกันก่อนอ้างว่าประวัติครอบคลุมทั้งหมด รวม reconcile แอดอัตโนมัติ นำเข้า รวมซ้ำ และล้าง/เก็บข้อมูล
- ตอนเปลี่ยนผ่านต้องหยุดเส้นทางเขียนของ client รุ่นเก่าที่ไม่สร้าง audit ให้รุ่นเก่าอัปเดตก่อนเขียนต่อ ไม่เปิดช่องให้แท็บเก่าหรือ API ตรงข้ามขั้นตอนประวัติได้
- หากผลกระทบมากเกิน transaction เดียว ต้องใช้ operation สถานะ pending/committed ที่กู้ทำต่อได้และไม่แสดงยอดครึ่งสำเร็จ ห้ามแยกเขียน record แล้วค่อยพยายามเขียนประวัติทีหลัง
- รูปและ attachment อ้างเวอร์ชันไฟล์ที่คงไว้ตามนโยบาย ไม่เก็บ base64 รูปซ้ำใน audit ทุกครั้ง และไม่ลบไฟล์เก่าถ้ายังต้องเปิดประวัติ/กู้คืนได้

ข้อกำหนดนี้เพิ่มขอบเขตจากการปรับ UI เดิม: ต้องกำหนด auth/สิทธิ์และปรับชั้นเขียนข้อมูล ไม่สามารถให้หลักฐานผู้แก้ที่เชื่อถือได้ด้วยการเก็บชื่อคนแก้ใน browser อย่างเดียว

## 6. ข้อมูลเก่า การเก็บถาวร และการคืนค่า

ข้อมูลเดิมมีประวัติแยกบางส่วน เช่น adjustments, stock batch edits, receiving corrections, แอด และรายการเงิน แต่ไม่ได้มี audit ครบทุกฟีเจอร์ ต้องย้ายโดยคงแหล่งที่มาเดิมและตรวจความสัมพันธ์

เมื่อเริ่มใช้ประวัติแบบใหม่ สร้าง baseline ที่ระบุวันเริ่มบันทึกและ revision ตั้งต้น ไม่อ้างว่าทราบผู้ทำ/ค่าก่อนหน้าที่ไม่มีหลักฐาน หากข้อมูลเก่าพอแก้ได้ให้ใช้ baseline ปัจจุบัน; หากรายละเอียดขาด ให้เริ่มรายการปรับปรุงที่ระบุเหตุผลและข้อมูลยืนยันใหม่ โดยคงรายการเก่าเชื่อมไว้

เก็บถาวรแทนลบรายการที่มีประวัติและ dependency ค้นเจอผ่านตัวกรอง “รวมเก็บถาวร” ID ไม่ถูกนำกลับมาใช้กับรายการใหม่ การรวมซ้ำคง alias และ snapshot เพื่อเปิดประวัติเก่าได้

การคืนค่าต้องใช้ข้อมูลเก่าเป็นข้อเสนอ แล้วเทียบกับสถานะล่าสุด ไม่ restore อาร์เรย์ทั้งชุดทับรายการที่เกิดภายหลัง กรณีคืนค่าทำตรง ๆ ไม่ได้ต้องมีทางปรับปรุง/แยกคืน/รับคืนตามความสัมพันธ์ พร้อมอธิบายสิ่งที่ต้องทำต่อ

ประวัติใหม่รวมใน backup version ใหม่อย่างมี schema และ compatibility: ไฟล์เก่าที่ระบบรองรับยังนำเข้าได้พร้อมบอกว่าประวัติบางส่วนไม่มี ไฟล์ใหม่ต้องมี record revision และ event ที่สัมพันธ์ครบ ไม่ล้าง audit ปัจจุบันเมื่อ import จากเครื่องอื่น

“ตลอดเวลา” หมายถึงไม่มีข้อจำกัดอายุรายการในการเข้าถึง/แก้สำหรับผู้มีสิทธิ์ และเก็บตามอายุการใช้งานข้อมูลที่ตกลง ไม่ใช่รับรองการเก็บข้อมูลส่วนบุคคลไม่จำกัดโดยข้ามนโยบายที่จำเป็น หากต้องลบข้อมูลส่วนบุคคล ให้แยกจากหลักฐานเชิงธุรกรรมและระบุว่าข้อมูลใดถูกลบแล้วตามนโยบาย

## 7. วันที่มีผลกับวันที่บันทึก

แสดงแยก `effectiveDate` กับ `recordedAt` เพื่อรู้ว่าแก้วันนี้แต่มีผลกับเดือนไหน รายงานมีมุมมอง “ยอดล่าสุดหลังปรับปรุง” กับ “snapshot ตอนออกรายงาน” พร้อมการเชื่อมเหตุการณ์แก้ไข

บันทึกกิจกรรมระบบอัตโนมัติเป็น actorKind=system และเก็บเหตุผล/ช่วงวันที่คำนวณใหม่ การแก้งบวันนี้ไม่แก้วันก่อน หากผู้ใช้ต้องการแก้วันก่อน ให้เลือกช่วงและยืนยันผลย้อนหลังอย่างชัดเจน

## 8. เกณฑ์ตรวจรับ P0

1. ฟีเจอร์ทุกแถวในตารางมีทางเข้าประวัติและทางแก้ไขที่ทำงานได้ทั้งมือถือและ desktop
2. การแก้รายการเก่า/ปิดแล้ว/เก็บถาวรไม่มีข้อจำกัดอายุ และมีทางปรับปรุงที่คงความถูกต้องตาม dependency
3. สร้าง แก้ ยกเลิก คืนค่า และงานอัตโนมัติทุกครั้งมี before/after, reason ตามกติกา, actor, revision และเวลา server
4. จำลอง failure ระหว่างบันทึกแล้วต้องไม่เกิดข้อมูลเปลี่ยนแต่ไม่มีประวัติ หรือมีประวัติสำเร็จแต่ข้อมูลไม่เปลี่ยน
5. กดซ้ำ/retry ได้ operation เดียว แก้พร้อมกันสองเครื่องมีเพียงหนึ่ง revision สำเร็จ อีกเครื่องตรวจความต่างก่อนลองใหม่
6. แก้จำนวนขาย/เงินรับ/ค่าส่ง/ต้นทุน/เครดิตแล้วรายการที่เชื่อม รายงาน และยอดคงเหลือตรงกัน ไม่ถือว่าเงินรับ/คืนเงินจริงเปลี่ยนตามจำนวนขาย
7. คืนค่าจากเวอร์ชันเก่าสร้าง revision ใหม่ และไม่ทำให้ธุรกรรมที่เกิดภายหลังหาย
8. เก็บถาวร/รวมซ้ำ/นำเข้าไม่ทำประวัติกำพร้าหรือปลอมที่มา actor
9. ค้นหาและกรองประวัติข้ามหน้าได้ ความสัมพันธ์ใน backup/import ผ่านการตรวจครบ
10. ผู้ไม่มีสิทธิ์แก้ข้อมูลหรือ audit โดยเรียก API ตรงไม่ได้; UI ที่ซ่อนปุ่มเพียงอย่างเดียวไม่ผ่าน

## 9. การเปลี่ยนลำดับพัฒนา

ตรึง Aurora และ schema ประวัติ → auth/สิทธิ์ + atomic mutation/audit → component ประวัติ/diff/review → ย้ายฟีเจอร์แต่ละส่วนพร้อมฟอร์มแก้ → ย้าย/สร้าง baseline ข้อมูลเก่า → regression และ rollout

ประวัติและแก้ไขเป็นส่วนของงานทุกโมดูลและต้องเสร็จก่อนปล่อยโมดูลนั้น รอบนี้เป็นการปรับแผนและแนวหน้าจอ ยังไม่ได้เพิ่ม audit collection หรือเปลี่ยนธุรกรรม production
